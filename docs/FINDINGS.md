# Security and Engineering Findings Register

This register records concrete security gaps, policy bypasses, supply-chain issues, and unimplemented controls discovered during Phase 0 baseline inspection and subsequent remediation passes.

| ID | Severity | Component | Description | Reproduction / Attack Vector | Status | Planned / Fixed Phase |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| FINDING-001 | High | `src/index.ts` | RBAC middleware (`server.use("mcp:tools/list", ...)` and `server.use("mcp:tools/call", ...)`) was not registered on `MCPServer`; `rbacManager.filterTools` was never invoked at runtime | Any MCP client calling `tools/list` received all registered tool descriptors regardless of caller credentials | FIXED | Phase 2 (P0-4: `src/index.ts`, `tests/server.test.ts`) |
| FINDING-002 | High | `src/index.ts` | Resource `schema://catalog` returned the full `TABLE_METADATA` object without authentication or role filtering | Reading `schema://catalog` without credentials exposed admin-only table names (`security_incidents`, `api_keys`) and PII column metadata | FIXED | Phase 2 (P0-4: `src/index.ts`, `tests/server.test.ts`) |
| FINDING-003 | High | `src/database/engine.ts` | Query timeout parameter `timeoutMs` was stored and echoed in response metadata, but synchronous `sql.js` ran on the main Node thread with no worker termination | A CPU-heavy recursive CTE blocked the Node event loop indefinitely despite the configured deadline | FIXED | Phase 2 (P0-1: `src/database/engine.ts`, `tests/sqlite-controls.test.ts`) |
| FINDING-004 | Medium | `src/database/engine.ts` | Response metadata reported a fixed memory cap string, while neither SQLite `max_page_count` nor Node Worker `resourceLimits` were configured | Large intermediate operations were bounded only by default process memory | FIXED | Phase 2 (P0-2: `src/database/sqlite-worker-code.ts`, `tests/sqlite-controls.test.ts`) |
| FINDING-005 | Low | `src/index.ts` | `verify_query_safety` response claimed native compiled AST evaluation, whereas `node-sql-parser` is a JavaScript PEG parser | Inspecting `verify_query_safety` output showed inaccurate implementation language wording | FIXED | Phase 1 (`src/index.ts`) |
| FINDING-006 | Critical | `src/security/validator.ts` | Derived-table subqueries in `FROM` (`SELECT x FROM (SELECT billing_email AS x FROM customers)`) bypassed both table authorization and PII column checks | `SELECT x FROM (SELECT webhook_secret AS x FROM api_keys)` as `analyst` passed `validator.validate()` | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `tests/pii-bypass.test.ts`) |
| FINDING-007 | Critical | `src/security/validator.ts` | Common Table Expressions (`WITH` clauses on `ast.with`) were not traversed by the validator | `WITH s AS (SELECT billing_email AS e FROM customers) SELECT e FROM s` as `analyst` passed `validator.validate()` | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `tests/pii-bypass.test.ts`) |
| FINDING-008 | Critical | `src/security/validator.ts` | Compound `SELECT` branches (`UNION`, `UNION ALL`, `INTERSECT`, `EXCEPT` chained via `ast._next`) were ignored after the first `SELECT` node | `SELECT id FROM customers UNION SELECT webhook_secret FROM api_keys` as `analyst` passed `validator.validate()` | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `tests/pii-bypass.test.ts`) |
| FINDING-009 | Critical | `src/security/validator.ts` | Column checks only inspected direct `col.expr.type === "column_ref"` nodes, allowing PII columns wrapped in functions, casts, binary expressions, or `CASE` expressions | `SELECT LOWER(billing_email) FROM customers` or `SELECT billing_email \|\| '' FROM customers` as `analyst` passed `validator.validate()` | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `src/security/result-policy.ts`, `tests/pii-bypass.test.ts`) |
| FINDING-010 | High | `src/security/validator.ts` | PII columns referenced inside `WHERE`, `GROUP BY`, `HAVING`, or `ORDER BY` were not checked, allowing character-by-character boolean inference | `SELECT id FROM customers WHERE billing_email LIKE 'b%'` as `analyst` leaked PII predicates | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `src/database/sqlite-worker-code.ts`, `tests/pii-bypass.test.ts`) |
| FINDING-011 | Medium | `src/security/validator.ts` | Implicit comma joins (`FROM customers a, api_usage b`) and non-equality tautologies (`ON 1`, `ON true`, `ON c.id = u.customer_id OR 1 = 1`) were not rejected by the `CROSS JOIN` check | `SELECT a.id FROM customers a, api_usage b` created an unconstrained Cartesian product | FIXED | Phase 2 (P0-5: `src/security/validator.ts`, `tests/validator.test.ts`) |
| FINDING-012 | Medium | `src/security/validator.ts` | `sqlite_master` and `sqlite_schema` were explicitly permitted for all roles, leaking full `CREATE TABLE` DDL of restricted tables | `SELECT sql FROM sqlite_master` as `analyst` revealed restricted schema definitions | FIXED | Phase 2 (P0-3: `src/security/validator.ts`, `src/database/sqlite-worker-code.ts`, `tests/sqlite-controls.test.ts`) |
| FINDING-013 | High | `src/security/rbac.ts` | Missing or invalid credentials silently granted `public_viewer` metadata access instead of failing closed by default | Unauthenticated callers could enumerate non-admin schemas and invoke `verify_query_safety` when no demo flag was set | FIXED | Phase 2 (P0-4: `src/security/rbac.ts`, `tests/rbac.test.ts`, `tests/server.test.ts`) |
| FINDING-014 | Medium | `src/security/validator.ts` | Function filtering used a denylist containing leftover DuckDB function names rather than an explicit SQLite scalar/aggregate allowlist | Unlisted SQLite functions (`printf`, `zeroblob`, `randomblob`, `sqlite_version`, unknown UDFs) were permitted by default | FIXED | Phase 2 (P0-3: `src/security/policy.ts`, `src/security/validator.ts`, `tests/validator.test.ts`) |
| FINDING-015 | High | `package.json` (`vitest` transitive `tinypool` / `@vitest/mocker`) | Running `pnpm audit` during P0-7 exposed 2 critical advisories in `tinypool < 2.1.2` (`GHSA-5gmw-xhrv-c9v3`, `GHSA-85c8-ppgw-ccpr`) and 3 moderate advisories in `@vitest/mocker` under `vitest@3.2.7` | Prototype pollution / code injection advisories in unpatched test runner dependency tree | FIXED | Phase 2 (P0-7: upgraded and pinned `vitest` to `5.0.5`; `pnpm audit` reports 0 vulnerabilities) |
| FINDING-016 | High | `src/database/postgres-adapter.ts` | The initial experimental adapter passed `{ readOnly: true }` in options but had no real `pg.Pool` connection, only returning simulated strings with no connection to a database | Queries executed against the adapter either failed or bypassed database-level authorization | FIXED | PostgreSQL Graduation (`src/database/postgres-adapter.ts`, `tests/postgres-adapter.test.ts`) |
| FINDING-017 | Medium | `src/database/postgres-adapter.ts` | Postgres connections without restricted `search_path` could be susceptible to schema search path spoofing if untrusted functions or tables were defined in public/temp schemas | Unqualified table references could resolve to unexpected schemas | FIXED | PostgreSQL Graduation (`SET LOCAL search_path = public, pg_temp`, `src/database/postgres-adapter.ts`, `tests/postgres-adapter.test.ts`) |
| FINDING-018 | High | `src/security/validator.ts` | `SQLValidator` only supported SQLite dialect. Postgres-specific syntax like type casting (`::TEXT`), double-quoted identifiers, or ILIKE threw parser errors or bypassed checks | Valid Postgres queries failed validation or dialect differences caused false rejections or undetected constructs | FIXED | PostgreSQL Graduation (`src/security/validator.ts`, `tests/postgres-adapter.test.ts`) |
| FINDING-019 | High | `docker/postgres/init/02-roles.sql` | Without database-level roles, query engine relied solely on AST parsing for RBAC and column hiding; an AST parser bypass would directly expose sensitive columns | If AST validator missed an aliased column, database returned the PII data | FIXED | PostgreSQL Graduation (`SET LOCAL ROLE`, least privilege roles `mcp_viewer`, `mcp_analyst`, `mcp_admin`, column grants, `docker/postgres/init/02-roles.sql`, `tests/integration/postgres-live.test.ts`) |
